01

Three projects, explicit boundaries

Application behavior, external operations and presentation have separate compile-time boundaries.

Dependency inversion where it helps

Core declares contracts used by its workflows; Infrastructure implements them; Desktop supplies the adapters. Interfaces stay with their consumers. IArchiveContents, for example, belongs to Infrastructure.

Manual composition and focused controllers

App and CommanderWindow wire the application. Desktop can call adapters directly when an interaction has no Core workflow. The code uses concrete views and controllers, without a mandatory DI container or universal view-model layer.

One Windows desktop application

C# / .NET 10, Avalonia 12.1.6 and its core TableView. SDK 10.0.102, pinned packages and lock files define the build. The supported profile is Release / Windows x64.

Launcher as a separate build mode

Permanent Xcmd.exe is a NativeAOT build of a small Infrastructure source subset, with isolated outputs and a separate lock file. In that mode it has no Core or UI dependency. It adds no fourth production project.

03

Navigation and refresh follow one path

Interactive input and headless tests reach the same controls, rules and adapters.

Latest request wins

PanelSession.LoadAsync cancels the previous load and ignores cancelled results. Successful reads sort entries, update history and increment the revision. Desktop applies rows and restores the cursor at explicit boundaries.

Refresh respects an active interaction

DirectoryMonitor watches physical directories. DirectoryUpdates waits for quiet and safe UI conditions. Inline rename, menus, dialogs, quick name search and feedback can defer application. Virtual archive locations are not watched.

Value-based navigation rules

PanelRules, DirectoryHistory, NameJump, FavoriteDirectories and usage/attention objects work with values. Desktop supplies time and handles key routing, focus and presentation.

Directory sizes reuse the filesystem port

DirectorySizeCalculator traverses through IFileSystem, excludes links and reports partial measurements. Desktop owns the active calculation, cancellation and displayed results.

04

File operations are explicit queued jobs

A request is captured once; progress, conflicts and partial changes remain observable.

Queued→Counting→Running⇄WaitingForConflict→terminal outcome

Planning, policy and execution

FileTransferPlanner interprets the destination. FileOperationRunner validates targets, inventories work, resolves conflicts and records outcomes. IFileOperationStore performs access. The serial queue owns ordering.

An asynchronous decision boundary

The runner awaits Func<FileConflict, CancellationToken, Task<ConflictDecision>>. Desktop waits for a safe dialog moment and returns Skip, Rename, Replace or Cancel. “Apply to all” is scoped to a run and conflict kind.

Completion has several meanings

Item outcomes include completed, skipped, failed, partial, cancelled and not-started. Job states distinguish errors, skipped work, cancellation and failure. Completed changes remain after cancellation; the current item can be partial. There is no rollback protocol.

Simple actions stay direct

Create-directory and inline rename still use IFileSystem from Desktop interactions. Copy, Move, Recycle and Delete use the richer queue. Not every file action is wrapped in the queue.

05

Archives adapt existing capabilities

Virtual locations reuse navigation, extraction reuses the copy queue, and F3 reuses the viewer.

A virtual location protocol

ArchivePath encodes a source and member with a | separator; display uses !. Parent and working-directory transformations are pure Core helpers. ArchiveFileSystem routes virtual reads and delegates regular paths.

Read-only contents, regular copy destination

Archive entry writes, moves, deletes and renames are rejected. Copying a member to a physical destination calls IArchiveContents.ExtractAsync through IFileOperationStore, preserving queue progress and cancellation.

One viewer for several sources

ArchiveViewerFiles resolves a member to a temporary file or an archive to a text report. It delegates paged reads and search to ViewerFiles. FileSlice defines a 16 KiB logical page; the window owns rendering and reading state.

Lifetime belongs to the adapter

ArchiveContents owns catalogs, materialized files and disposal. ArchiveController owns the archive service for panels/viewers. Search creates its own source and archive service. These are explicit lifetimes, rather than one global cache.

06

Search separates scope, work and presentation

The working tree implements a multi-lane pipeline with explicit skipped coverage.

Scope policy belongs to Core

FileSearchScope defers Git-ignored candidates and common heavy directories. Tracked paths override deferral. SearchGitScope reads classification from Git in windowless processes; FileSearchSource translates it into Core values.

Small content work has its own lane

Two consumers scan physical files up to 1 MiB; one scans larger files. Archive traversal and archive text have separate channels. Traversal is breadth first with local entry ordering; it does not measure subtree sizes to globally rank directories.

Decode, then search

SearchText samples up to 64 KiB, detects encoding, skips binary samples and tries encoding fallbacks when needed. Literal search scans chunks with overlap. Regex runs per line with a 100 ms match timeout and a 256 KiB line limit. Matches carry code pages into the viewer.

Desktop owns replacement and batching

FileSearchWindow owns source disposal, cancellation and a concurrent incoming queue. A 60 ms timer flushes results into actual controls. A new query retires the previous request; expansion keeps existing results and scans deferred locations.

Coverage limits are explicit data: traversal stops above 200,000 visited entries or at 20,000 emitted results. Links are not followed; nested archive contents are not searched. Stops, limits, deferred locations and failures remain visible. One result is emitted per matching path.

07

Persistence enables safe release handoff

The replacement becomes ready before the old process closes; visible startup waits for old-process exit.

Permanent entry, immutable releases

BootstrapProgram validates the marked release and forwards arguments plus the caller’s working directory. Publishing creates a new directory and atomically switches releases/latest.txt after phase-specific checks and launcher installation. release.json declares restart protocol 1.

An explicit idle gate

RestartReadiness.CanRestart requires two seconds without input and no busy work, editing, dialogs or feedback. Desktop includes command focus, open search/viewer windows, pointer drag and inline rename in readiness inputs.

A strict restart contract

RestartProcess launches with --session, --handoff and --wait-for. The replacement requires a valid restored workspace, writes a ready file and waits for the old process. An invalid restart does not silently become an empty session.

Feedback is durable application state

FeedbackController and FeedbackSurface provide comments across windows. Notes identify element, directory and release, with optional interaction records. WorkspaceLifecycle immediately saves the session and compiles refinements.md; records survive handoff.

Related boundary: command input and external programs

CommandLine parses local cd and external commands and owns history rules in Core. Desktop captures the working directory and command editor state. IExternalLauncher carries an ExternalLaunch request to WindowsExternalLauncher. ShellExecute starts the target; Xcmd does not host a terminal. WindowsLaunchEnvironment serializes a temporary refreshed environment override around launch and restores it afterward. External programs retain their own lifetime.

08

Test seams are part of the design

The production controls can be exercised without visible application windows.

Readable cases, reusable drivers

tests/Xcmd.Probe/Scenarios expresses user actions and outcomes. Drivers, fixtures, process hosts, rendering, timing and cleanup live in Infrastructure. Test infrastructure must not depend on scenario cases.

Real controls and integration boundaries

ProbeAppBuilder configures Avalonia.Headless with Skia. Cases use actual windows, handlers and state, plus isolated files and archive samples. Xcmd.LaunchProbe is a windowless endpoint for the production Windows launch contract.

Mechanically enforced boundaries

ArchUnitNET and evaluated reference allowlists protect the layers. API bans keep raw filesystem, process and native access out of Core/Desktop and ambient time/environment reads out of Core. Analyzers and metrics reject blocking calls and configured complexity violations.

Evidence has a scope

Headless checks do not establish native monitor placement, desktop focus, third-party editor appearance or shell-extension menu appearance. This page describes inspected implementation and test seams. Generating it does not rerun the application suite or prove that this working tree passes.
