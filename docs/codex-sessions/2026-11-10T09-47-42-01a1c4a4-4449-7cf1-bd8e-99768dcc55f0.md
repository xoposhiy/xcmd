### Codex final reply

> Да, здесь стоит добавить **постоянный запускатель**, сохранив нынешние отдельные папки версий.
>
> Сейчас можно сделать ярлык на конкретный `Xcmd.Desktop.exe`: он откроет эту версию, а затем приложение сможет автоматически перейти на новую. Но ярлык останется привязан к старой папке. Полностью твою задачу текущая схема пока не решает.
>
> Я рекомендую такую процедуру:
>
> 1. Постоянный `C:\work\projects\xcmd\Xcmd.exe` читает `releases/latest.txt`.
> 2. Проверяет указанный релиз и запускает его, передавая аргументы и рабочую папку.
> 3. Сразу завершается. Всё приложение продолжает работать из `releases/<release-id>`.
> 4. Новые релизы публикуются как сейчас: проверка, отдельная папка, затем атомарная замена маркера. Неудачный релиз целью запуска не становится.
>
> Сам запускатель при обычном релизе обновлять не нужно. Поэтому работающее приложение держит файлы своей версии, а выпуск следующей версии свободно продолжается.
>
> Для таскбара нужна ещё одна часть: **единый идентификатор приложения во всех версиях и готовый ярлык на постоянный запускатель**. Это позволит Windows связывать закреплённую кнопку с окнами разных релизов. Microsoft прямо описывает такую схему для приложений с отдельным запускателем. [Документация Windows](https://learn.microsoft.com/en-us/windows/win32/shell/appids).
>
> Также нужно обеспечить, чтобы закрепление из работающего окна вело на запускатель. Для этого Windows поддерживает отдельную команду повторного запуска. [Механизм закрепления и запуска](https://learn.microsoft.com/en-us/windows/win32/properties/props-system-appusermodel-relaunchcommand).
>
> В результате ты один раз закрепляешь **Xcmd**, создаёшь на него любые ярлыки, и дальнейшие релизы этих ярлыков не касаются. Текущие три проекта, сохранение сессии и автоматическую смену работающей версии можно сохранить. Изменение касается точки входа и интеграции с Windows.
